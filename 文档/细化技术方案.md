# 细化技术方案：面向颗粒堆积体的实时仿真与渲染系统

> 本文档用于指导 RTVK 后续开发流程。重点不是一次性列出所有理想功能，而是明确当前状态、模块边界、阶段目标、验收标准和风险控制。
> 技术栈：C++17 + Qt Widgets + Vulkan 1.3 + GLSL/SPIR-V + CMake。

---

## 一、开发目标与当前基线

### 1.1 总体目标

构建一个可交互、可验证、可扩展的颗粒堆积体实时仿真与渲染系统，支撑论文中“物理真实性与实时性能兼顾”的核心论点。系统最终应支持：

- 10000 级别颗粒的实时仿真，目标帧率不低于 30 FPS。
- 沙、土、煤三类颗粒材料的差异化物理参数与渲染表现。
- PBD 约束求解、空间哈希邻域搜索、基础碰撞与堆积行为。
- 从简单点精灵渲染逐步过渡到屏幕空间表面重建和材质渲染。
- 文本驱动的参数配置入口，后续扩展到多模态交互。
- 可复现实验数据，包括性能、稳定性、渲染质量和交互准确性。

### 1.2 当前项目状态

当前代码已经具备以下基础能力：

| 模块 | 当前状态 | 后续重点 |
|------|----------|----------|
| UI | 已有 Qt Widgets 主窗口，左侧控制栏、右侧 Vulkan 视口，支持运行/暂停 | 完善参数面板、状态栏、调试信息 |
| CPU PBD | `src/sim/pbd_solver.*` 已实现基础 PBD 流程 | 作为 GPU 求解的参考实现和单元测试基准 |
| GPU 仿真 | `shaders/sim/*.comp` 与 `GranularVulkanWindow` 已形成基础 compute 闭环 | 稳定空间哈希、约束投影、同步和数据布局 |
| 渲染 | 已有简单粒子点精灵渲染，用于验证仿真结果 | 扩展到深度、法线、屏幕空间重建和材质 |
| 构建 | CMake + Qt + Vulkan + shader 编译流程已搭建 | 保持 shader、C++ 数据结构和输出目录一致 |

当前开发应优先围绕“仿真正确性可见、可暂停、可调参、可测量”推进。复杂渲染和 LLM 交互必须建立在稳定仿真闭环之后。

为了和实际开发进度对齐，后续阶段按工程闭环重新组织：

## 二、总体架构

### 2.1 模块划分

项目当前目录与职责如下：

| 路径 | 职责 | 开发原则 |
|------|------|----------|
| `src/core` | 全局配置、公共数据结构、数学/参数基础 | 保持轻量，不放 UI 或 Vulkan 细节 |
| `src/sim` | CPU 参考仿真、PBD 数据结构、空间哈希参考实现 | 作为正确性基准，优先可读和可测试 |
| `src/render` | Vulkan 设备、图形管线、compute 管线、粒子渲染 | 明确资源生命周期，严控 buffer/shader 布局 |
| `src/ui` | Qt 主窗口、控制面板、用户操作入口 | 只调度参数和状态，不直接实现物理算法 |
| `shaders/sim` | GPU 仿真 compute shader | 与 C++ 数据结构逐字段对齐 |
| `shaders/particle` | 当前粒子测试渲染 shader | 后续逐步迁移到屏幕空间渲染 |
| `tests` | PBD、空间哈希、Vulkan 基础测试 | 每个核心行为至少有一个可复现验证 |

### 2.2 数据流

当前运行时主数据流如下：

```text
Qt UI
  |
  | 用户点击运行/暂停、后续调整参数
  v
MainWindow
  |
  | 创建初始颗粒数据，启动仿真 timer
  v
GranularVulkanWindow
  |
  | gpuSimStep()
  v
Compute Pipeline
  |
  | integrate.comp -> spatial_hash.comp -> compact.comp -> constraint.comp -> integrate.comp
  v
GPU Particle Buffer
  |
  | 当前阶段读回到 CPU，再更新粒子顶点 buffer
  v
Particle Graphics Pipeline
  |
  v
右侧 Vulkan 视口
```

后续优化目标是减少 CPU 读回，让 graphics pipeline 直接读取 compute 输出的 GPU buffer。但在当前阶段，读回路径可以保留，因为它有助于调试和验证。

### 2.3 关键数据布局约定

GPU 颗粒结构体必须同时满足 C++ 与 GLSL `std430` 布局。当前约定：

```text
offset  size  字段
0       12    position
12      4     padding
16      12    velocity
28      4     padding
32      12    predictedPos
44      4     invMass
48      4     radius
52      4     padding
56      4     padding
60      4     padding
stride  64
```

开发规则：

- C++ 侧 `GpuParticle` 必须使用 `static_assert(sizeof(...))` 和 `offsetof(...)` 校验关键字段。
- shader 中新增结构体字段时，必须同步更新 C++ 结构体、上传逻辑、读回逻辑和文档。
- 所有 Vulkan 坐标转换必须明确是否进行了 Y 轴翻转、深度范围适配和相机矩阵处理。

## 三、仿真方案

### 3.1 PBD 基础流程

每一帧仿真执行以下流程：

```text
1. 外力积分：v_i = v_i + dt * f_ext / m_i
2. 预测位置：p_i = x_i + dt * v_i
3. 邻域搜索：根据 predicted position 构建空间哈希
4. 约束投影：修正接触、地面和边界约束
5. 速度回写：v_i = (p_i - x_i) / dt
6. 位置提交：x_i = p_i
```

CPU 版 `PBDSolver` 的职责是提供可读、可测、可对照的参考行为。GPU 版的目标是与 CPU 行为在趋势上保持一致，再逐步追求性能。

### 3.2 近期必须稳定的物理行为

阶段四的验收不以复杂效果为目标，而以基础行为正确为目标：

| 行为 | 预期结果 | 验证方式 |
|------|----------|----------|
| 重力下落 | 粒子沿世界坐标 Y 负方向下落，屏幕表现方向正确 | 运行视口观察，或读回位置比较 |
| 地面碰撞 | 粒子不低于 `domainMin.y + radius` | 单元测试与调试输出 |
| 边界约束 | 粒子不穿出 X/Z 范围 | 读回最大/最小坐标 |
| 粒子间接触 | 明显重叠会被逐步修正 | 比较最小粒子距离 |
| 暂停/恢复 | 暂停后位置保持不变，恢复后继续推进 | UI 操作验证 |

### 3.3 PBD 改进点：自适应约束分层求解

开题分析指出，PBD 已是成熟方法，论文需要明确“改进点”。本项目建议将改进点收敛为一个可实现、可实验对比的方向：自适应约束分层求解。

核心思想：

- 将约束分为刚性层和柔性层。
- 刚性层处理地面、边界、接触穿透，优先保证稳定。
- 柔性层处理摩擦、黏结、材料差异，允许较少迭代。
- 根据上一帧平均残差或穿透深度动态调整迭代次数或松弛因子。

建议先实现最小版本：

| 层级 | 约束 | 迭代策略 | 首次实现 |
|------|------|----------|----------|
| L1 | 地面、边界、接触 | 每帧固定 5 次 | 必做 |
| L2 | 摩擦 | 每帧 1-2 次 | 第二步 |
| L3 | 黏结/湿土效果 | 条件启用 | 第三步 |
| 自适应 | 根据穿透残差调节迭代 | 记录指标后启用 | 实验阶段 |

### 3.4 物理参数模型

| 参数 | 沙 | 土 | 煤 | 开发用途 |
|------|----|----|----|----------|
| 颗粒半径 | 中 | 中 | 中 | 影响渲染和碰撞半径 |
| 摩擦系数 | 0.6 | 0.8 | 0.5 | 控制堆积稳定性 |
| 黏结强度 | 0.0 | 0.5-2.0 | 0.0 | 控制湿土/泥土表现 |
| 恢复系数 | 0.3 | 0.1 | 0.4 | 控制弹性反应 |
| 休止角 | 30-35 度 | 35-45 度 | 25-30 度 | 用于实验评价 |

开发优先级：

1. 先让所有材料共用稳定 PBD。
2. 再通过摩擦系数区分沙、土、煤。
3. 最后增加黏结约束和湿度参数。

## 四、GPU Compute 开发路线

### 4.1 当前 compute 管线

当前 GPU 仿真包含以下 shader：

| Shader | 职责 | 近期检查点 |
|--------|------|------------|
| `integrate.comp` | 外力积分、预测位置、速度回写 | `invMass`、`radius` 布局正确，dt 稳定 |
| `spatial_hash.comp` | 计算粒子 cell hash，写入桶统计 | hash 分布合理，无越界 |
| `compact.comp` | 前缀和与粒子索引压缩 | startOffset/count 与粒子数一致 |
| `constraint.comp` | 邻域约束投影、地面和边界约束 | 迭代后穿透下降 |

### 4.2 GPU 开发顺序

GPU 侧不要一次性追求完整物理模型。建议按以下顺序推进：

1. 固定少量粒子，验证 `integrate.comp` 的位置和速度变化。
2. 打开地面约束，验证下落后停在地面上方。
3. 打开空间哈希，只统计 cell，不做粒子间约束。
4. 打开接触约束，验证少量粒子不会明显重叠。
5. 扩大到 1000、5000、10000 粒子，记录耗时和稳定性。
6. 加入摩擦和材料参数。
7. 再考虑异步 compute、直接 GPU 渲染和读回优化。

### 4.3 每次修改 GPU shader 后必须检查

- `.comp` 是否重新编译为 `.spv`。
- 输出目录是否复制了最新 `.spv`。
- C++ descriptor binding 是否与 shader binding 一致。
- specialization constant 的数量、类型、offset 是否一致。
- push constant 的 offset 是否符合 shader 反汇编结果。
- GPU buffer stride 是否与 shader 结构体数组 stride 一致。

建议保留一个调试命令，用 `spirv-dis` 检查关键结构体 offset。

## 五、渲染方案

### 5.1 渲染分阶段目标

渲染模块不要过早进入完整屏幕空间管线。建议分三层推进：

| 层级 | 目标 | 用途 |
|------|------|------|
| R1 简单粒子渲染 | 点精灵显示所有粒子，方向和位置正确 | 验证仿真 |
| R2 增强粒子渲染 | 深度、伪球面法线、材质颜色、基本光照 | 演示与调试 |
| R3 屏幕空间表面重建 | G-Buffer、双边滤波、法线重建、PBR | 论文效果展示 |

当前项目处于 R1。R1 必须保持简单稳定，不应被复杂后处理影响调试。

### 5.2 当前粒子渲染验收标准

- 相机视角能清楚看到颗粒堆。
- Vulkan Y 轴方向处理正确。
- 暂停时画面位置稳定。
- 粒子数量变化时 vertex buffer 能正确扩容。
- 视口 resize 后能继续渲染。

### 5.3 屏幕空间渲染路线

在 R1 稳定后，再进入 R3：

```text
Pass 1: 粒子深度/颜色输出
Pass 2: 深度双边滤波，填补粒子间空洞
Pass 3: 从深度重建位置和法线
Pass 4: 材质光照，区分沙、土、煤
Pass 5: SSAO、Tone Mapping、FXAA
```

开题分析提醒屏幕空间方法存在遮挡和离屏局限。因此论文中应明确：

- 屏幕空间重建主要服务于当前视角下的实时外观增强。
- 离屏粒子不会参与当前屏幕重建。
- 对严重遮挡场景，可用粒子点精灵或多层深度作为混合方案。

## 六、UI 与交互路线

### 6.1 当前 UI 目标

当前 UI 应服务于开发调试，而不是先做完整产品界面。左侧控制栏优先提供：

| 控件 | 状态 | 行为 |
|------|------|------|
| 运行/暂停 | 已实现 | 停止/恢复仿真 timer |
| 重置模拟 | 待实现 | 重新上传初始颗粒，清空速度 |
| 材质参数 | 待实现 | 切换沙/土/煤参数 |
| 调试信息 | 待实现 | 显示粒子数、FPS、compute 耗时 |
| 截取画面 | 待实现 | 用于实验截图和论文素材 |

### 6.2 参数面板优先级

后续参数面板建议按以下顺序实现：

1. 粒子数量、半径、重力、迭代次数。
2. 材料类型：沙、土、煤。
3. 摩擦、恢复系数、黏结强度。
4. 渲染参数：点大小、基础颜色、光照强度。
5. 性能参数：是否读回、是否显示调试统计。

每个参数都应有默认值、合法范围和重置行为。

### 6.3 LLM 交互最小可行版本

LLM 模块应晚于参数面板。最小可行版本只做“文本到结构化参数”：

```json
{
  "scene_type": "sand",
  "particle_count": 10000,
  "physics": {
    "friction": 0.6,
    "cohesion": 0.0,
    "restitution": 0.3,
    "gravity": 1.0
  },
  "rendering": {
    "roughness": 0.9,
    "metallic": 0.0,
    "albedo": [194, 178, 128]
  },
  "simulation_mode": "pile",
  "description": "干燥沙堆"
}
```

必须包含：

- JSON schema 校验。
- 参数范围裁剪。
- 解析失败回退默认值。
- 用户确认后再应用到仿真。

图片解析可以作为扩展，不作为主线阻塞项。

## 七、开发里程碑与验收标准

### 7.1 阶段四：PBD 行为稳定化

目标：让基础颗粒在 GPU 路径中稳定下落、碰撞、堆积。

任务：

- 修正并锁定 GPU/C++ 粒子数据布局。
- 完善地面和边界约束。
- 验证空间哈希结果。
- 修复明显穿透、静止、方向错误问题。
- 增加基础调试输出或读回检查。

验收：

- 1000 粒子下落到地面后稳定。
- 暂停/恢复行为正确。
- 运行 60 秒无崩溃、无明显 NaN 或越界。
- CPU 参考结果与 GPU 结果在趋势上相符。

### 7.2 阶段五：开发控制台与调试工具

目标：让后续开发不依赖猜测。

任务：

- 实现重置模拟。
- 显示粒子数、FPS、仿真状态。
- 显示 GPU compute 耗时或至少每帧耗时。
- 参数面板接入 `SimParams`。
- 增加 shader/buffer 布局检查文档或脚本。

验收：

- 可在 UI 中调整基础参数并重新初始化仿真。
- 参数变化不会导致 Vulkan 资源泄漏或崩溃。
- 关键状态能在界面或日志中看到。

### 7.3 阶段六：渲染效果增强

目标：从“能看见粒子”过渡到“有颗粒材料外观”。

任务：

- 改善粒子点精灵光照。
- 增加材质颜色和粗糙度参数。
- 记录深度信息，为屏幕空间重建做准备。
- 实现基础 G-Buffer 或等价中间纹理。

验收：

- 沙、土、煤在颜色和粗糙感上可区分。
- 简单渲染路径仍可作为调试开关保留。
- 渲染修改不影响 PBD 稳定性。

### 7.4 阶段七：屏幕空间重建与实验

目标：支撑论文第四章和实验章节。

任务：

- 深度滤波与空洞填补。
- 法线重建。
- PBR 或近似 PBR 光照。
- SSAO/Tone Mapping/FXAA 选择性启用。
- 准备渲染质量对比实验。

验收：

- 与简单粒子渲染相比，表面连续性明显提升。
- 有截图、帧率、GPU 时间数据。
- 说明屏幕空间方法局限和适用范围。

### 7.5 阶段八：LLM 参数映射与系统集成

目标：支撑系统完整性和交互创新点。

任务：

- 文本输入到 JSON 参数。
- 参数校验和用户确认。
- 将参数应用到仿真和渲染。
- 记录成功率、失败样例和回退策略。

验收：

- 常见输入如“干燥沙堆”“湿土滑坡”“煤堆”能生成合理参数。
- 错误输入不会破坏当前场景。
- 论文中能说明交互链路和稳定性策略。

## 九、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| PBD 创新性不足 | 论文贡献不清晰 | 聚焦自适应约束分层，并设置对比实验 |
| GPU shader 调试困难 | 容易出现静止、NaN、越界 | 保持 CPU 参考实现，使用读回和 SPIR-V offset 检查 |
| C++/GLSL 布局错位 | 产生隐蔽 bug | 使用 `static_assert`、`offsetof`、反汇编检查 |
| 屏幕空间渲染局限 | 遮挡和离屏场景效果不稳定 | 论文中说明适用范围，保留粒子渲染回退 |
| LLM 输出不稳定 | 参数错误影响仿真 | schema 校验、范围裁剪、用户确认、默认回退 |
| 时间有限 | 功能堆叠导致主线不稳 | 先保证仿真闭环，再做渲染增强，最后做 LLM |

## 十、开发检查清单

### 10.1 修改仿真代码前

- 明确修改发生在 CPU 参考路径还是 GPU 运行路径。
- 明确是否影响 `GpuParticle`、shader struct、descriptor binding。
- 明确是否需要更新单元测试或读回验证。

### 10.2 修改 shader 后

- 重新编译 `.spv`。
- 确认运行目录中的 `.spv` 已更新。
- 检查 push constant、specialization constant、descriptor set。
- 必要时用 `spirv-dis` 查看 offset。

### 10.3 修改 UI 后

- 确认 resize 后 Vulkan 子窗口跟随变化。
- 确认按钮状态和仿真状态一致。
- 暂停时不应推进仿真，但渲染窗口可继续刷新。

### 10.4 提交前

- 检查 `git status`，只提交本次任务相关文件。
- 不提交 `build/`、`vk.log`、`*.spv`。
- 说明本次修改解决的问题、原因和验证方式。
